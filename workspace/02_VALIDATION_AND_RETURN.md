# Проверки и формат возвращаемой работы

## Проверка исходного пакета

`python3 tools/verify_package.py` сверяет SHA/размеры исходных файлов. Это проверка комплектации, не проверка всех механик приложения. Сначала выполни её до редактирования; после изменений несоответствие изменённых файлов исходному MANIFEST ожидаемо. Само приложение не требует установки зависимостей.

## Проверки выбранного приложения

Для браузерных тестов нужны Python Playwright и Chromium; текущие скрипты обычно используют /usr/bin/chromium. Другой путь задаётся в скриптах, где предусмотрен аргумент. Node нужен для модельных тестов Next и некоторых валидаций. Зависимости устанавливаются по правилам среды, без запроса реальных секретов/ключей.

Примеры из корня распаковки; запускай только относящиеся к задаче:

```sh
# Основная Personal: отдельный HTTP-сервер на 8041 должен уже работать.
python3 personal/tests/browser.py http://127.0.0.1:8041

# Родительская лаборатория: свой браузерный набор при том же сервере.
python3 personal-lab/tests/browser.py http://127.0.0.1:8041

# Самостоятельные приёмочные наборы экспериментов поднимают свой локальный сервер.
python3 personal-lab/experiments/flexible-complexity/tests/verify.py
python3 personal-lab/experiments/ai-strategy/tests/verify.py

# Next: модельный набор; отдельные браузерные команды — next/README.md.
npm test --prefix next

# Воспроизведения последнего UX-пилота: свежая папка вывода, свой сервер.
python3 personal-lab/research/LAB-015-live-pilot/reproductions/reproduce.py --help
```

Файлы model-cases.js — части браузерных harness, их не нужно запускать напрямую как отдельные Node-тесты. Временные JSON/PNG/profiles выводятся в verification/ и не должны заменять исходные кодовые файлы или реальные данные.

**Ограничения без Git:** personal-lab/tests/daily-ux.py получает старые ресурсы через git show 50bfec… для настоящего v1→v2 обновления; сборщик прежнего пакета LAB-014 тоже использует исходные Git-объекты. Эти файлы включены как код, но соответствующая история не входит в этот пакет. Для них нужен исходный checkout/отдельные исторические фикстуры. Не делай вид, что наличие файла равнозначно возможности выполнить такой тест. Путь к Git-копии и фикстуры можно запросить у координатора, если это необходимо поставленной задаче.

**Полные доказательства:** LAB-015 содержит отчёт, семантическую сверку и выбранные переносимые PNG/JSON. Полные traces/прошлые ZIP намеренно не приложены. Ссылки старых отчётов на них ведут к исходному репозиторию/исходной среде, а не к скрытым файлам этого ZIP. При необходимости запросить конкретный пакет, а не выдумывать содержимое. Интернет-исследование «ГИДРЫ» и её примеры не являются реальными UX-результатами.

## Что вернуть

Архив с исходными относительными путями, содержащий только изменённые/новые файлы, и два коротких документа:

- CHANGE_SUMMARY.md: цель/область, исходный commit, какие оригиналы менялись и их исходные SHA, поведение до/после, влияние на данные/экономику, принятые решения, риски и незавершённое.
- TEST_RESULTS.md: фактическая команда/среда/результат, что запускалось и что только изучено, ошибки/исправления, оставшаяся ручная приёмка. Скриншоты/минимальный воспроизводящий пример — при пользе для проверки.

Не присылай весь прежний репозиторий, зависимости, browser profiles или новые большие архивы истории. Код и утверждения внешней модели будут сверяться координатором с текущими файлами: с момента передачи они могли измениться. Не восстанавливай старую версию поверх чужой работы только ради совпадения с MANIFEST.

Для самостоятельного Git-checkout координатору достаточно исходного commit/SHA и diff. Для обычной распаковки верни точные файлы с сохранёнными путями и списком изменений; выдуманный Git patch без настоящей базы не нужен.
