## 1. Сводка адресных исправлений `R01–R04` в выпуске `v2.1.1` (по заданию `LAB-010-R2`)

### `R01` (P2) — Единое значение по умолчанию `rare_gems_quota = 0` в `SCORING.md` и `PASTE/*.txt`
* **Наблюдение в v2.1:** В `SCORING.md` (строка 95) внутри описания Фазы 2 оставалась старая пометка `(по умолчанию 25)`, противоречащая строке 98 того же раздела (`по умолчанию 0`), коду `configuration()` и `templates/RUN.json`. При пересборке `PASTE/02`, `PASTE/03` и `PASTE/05` это противоречие копировалось в автономные тексты.
* **Что изменено в v2.1.1:**
  1. В `SCORING.md` убрана фраза `(по умолчанию 25)` и зафиксирована единая формулировка: по умолчанию `0` до калибровки, а ненулевая квота (например, `25`) возможна только как явно заданный параметр конкретного `RUN.json` после выбора политики.
  2. Исторический протокол `HYBRID_V2_DECISION_RECORD.md` сохранён без переписывания истории.
  3. Пересобраны все 4 файла `PASTE/*.txt` и обновлены `input_hashes` в `starter_tasks/CAL-SEARCH-01..04.json`.
  4. Добавлен автотест `24_R01_single_default_quota_in_scoring_and_paste`, проверяющий отсутствие конфликта в `SCORING.md` и всех файлах `PASTE/*.txt`.

### `R02` (P1) — Байтовый бюджет навигационного индекса, короткое `preview` и маркировка сверхкрупных записей
* **Наблюдение в v2.1:** При нарезке `shard_findings()` строка компактного индекса включала полный текст `description`, а сам индекс делился только по числу строк (`index_max_records`). В результате одна находка с `description` из 150 000 кириллических символов (300 КБ) раздувала навигационный индекс до `300 125` байт без флага превышения в индексе.
* **Что изменено в v2.1.1:**
  1. В `shard_findings()` добавлены параметры `--index-max-bytes` (по умолчанию `60 000` байт, адаптивно ограничивается `min(index_max_bytes, max_bytes)`) и `--preview-chars` (по умолчанию `160` символов).
  2. Навигационный индекс (`compact_findings_index_partNNN.txt`) теперь содержит только ID, коды, статус (`STANDARD` или `OVERSIZED_BUNDLE:<reason>`), точные имена файлов полного материала (`part=... | sources=...`), название и короткое `preview`.
  3. Если `description` длиннее `preview_chars`, в индексе ставится явная метка: `[PREVIEW_TRUNCATED_AT_<preview_chars>_OF_<total>_CHARS; FULL_IN=<part_file>]`. Сам полный текст `description` сохраняется **побайтово и без малейшей обрезки** в JSONL-файле соответствующей части.
  4. В `shards_manifest.json` для каждого тома `index_parts` публикуются `records`, `bytes`, `contains_oversized_records`, `oversized_record_ids` и `truncated_previews_count` (подтверждено автотестом `25_R02_bounded_index_preview_and_oversized_marker`).

### `R03` (P1) — Полный байтовый бюджет автономного пакета (`findings + deduplicated sources + prompt reserve`)
* **Наблюдение в v2.1:** Лимит `max_bytes` проверял только размер `findings.jsonl`, не учитывая приложенный файл источников `.sources.jsonl`. На фикстуре из 60 небольших находок (40 620 байт) и 60 источников с длинными `notes` (397 200 байт) создавался обычный немаркированный пакет суммарным размером `437 820` байт при лимите `120 000`.
* **Что изменено в v2.1.1:**
  1. Лимит `--max-bytes` (в манифесте `max_packet_total_bytes`, по умолчанию `120 000` байт) теперь ограничивает **полный размер автономного задания**:
     $$\text{total\_bytes} = \text{findings\_bytes} + \text{sources\_bytes (дедуплицированные по ID внутри части)} + \text{prompt\_reserve\_bytes}$$
     При этом поддерживается и отдельный потолок `--max-findings-bytes` (по умолчанию равен `max_bytes`).
  2. При добавлении очередной находки в текущую часть вычисляется точный прирост `added_s_bytes` только для тех `source_ids`, которых ещё нет в `current_sids` этой части (общие источники не считаются дважды и не теряются). Как только добавление находки превышает `max_records`, `max_findings_bytes` или полный бюджет пакета `max_bytes`, текущая часть закрывается и открывается следующая.
  3. Если **одна-единственная находка вместе со своими обязательными источниками и резервом промта** превышает `max_bytes` (или `max_findings_bytes`), она никогда не маскируется под обычный пакет, а выделяется в отдельную часть с явным статусом `"packet_status": "oversized_single_bundle"`, `"oversized_single_record": true` и записью в `oversized_single_records` с полями `findings_bytes`, `sources_bytes`, `prompt_reserve_bytes`, `total_bytes` и `reason`.
  4. На контрольном тесте с 60 находками и 60 источниками с `notes` (суммарно ~438 КБ) при лимите `120 000` байт теперь создаётся **4 стандартных ограниченных пакета** (каждый `total_bytes <= 120 000` байт, подтверждено автотестом `26_R03_total_packet_budget_including_sources_and_oversized_bundle`).

### `R04` (P2) — Атомарная публикация `prepare-blind` без перезаписи конкурирующего выпуска
* **Наблюдение в v2.1:** Между проверкой `if out.exists()` и вызовом `os.replace(temp_path, out)` существовало окно гонки (TOCTOU): если конкурирующий процесс успевал опубликовать файл `out` непосредственно перед `os.replace()`, он молча перезаписывался.
* **Что изменено в v2.1.1:**
  1. В `prepare_blind_packet()` вызов `os.replace()` заменён на атомарный системный вызов жёсткого связывания без перезаписи `os.link(temp_path, out)` (с резервным `os.open(str(out), os.O_WRONLY | os.O_CREAT | os.O_EXCL)` для файловых систем без hardlink), а удаление временного `temp_path` обёрнуто в блок `finally`.
  2. Поскольку `os.link` и `O_CREAT | O_EXCL` атомарно отказывают на уровне ядра ОС (`FileExistsError`), если целевое имя уже существует в момент публикации, конкурирующий файл остаётся на 100% нетронутым, второй процесс получает чистый `ValueError("Blind packet output appeared concurrently during execution; refusing to overwrite")`, а временный `blind-pkt-*` файл гарантированно удаляется (подтверждено автотестом `27_R04_atomic_no_overwrite_blind_publication_and_staging_cleanup`).

## 2. Сводка ранее закрытых замечаний `H1–H8` в выпуске `v2.1` (по заданию `LAB-008-R1`)

* **`H1` (Целостность ZIP-архива и исключение `__pycache__`):** В `tools/atlas.py` включён `sys.dont_write_bytecode = True`, а `manifest()` фильтрует `__pycache__`, `*.pyc/pyo`, `.DS_Store`.
* **`H2` (Единая политика агрегации `Q`):** Медианы `m[d]`, `Q`, `Q_min`, `Q_max` вычисляются строго по полным слепым оценкам (`complete_rs`, минимум 2 полные оценки), а проверка конфликтов (`max - min >= 2`) охватывает все известные числовые значения во всех слепых оценках (`all_blind_rs`).
* **`H3` (Разбиение 10 000 однотипных находок):** Нарезка `shard` формирует нумерованные части `SHARD_<Phase>__<Friction>__partNNN.jsonl` с приложенными `.sources.jsonl` и 100% сохранением всех ID.
* **`H4` и `H5` (Защита выходов `shard` и границ путей):** `shard_findings()` отказывается писать в существующий каталог или пересекаться со входом, вызывает `validate()` до записи и проверяет токены по `SAFE_CODE_RE`.
* **`H6` (Защита входа и существующего файла в `prepare-blind`):** `prepare_blind_packet()` отвергает существующие выходные файлы и пути внутри входной папки `dataset_dir`.
* **`H7` (Строгая валидация `rare_gems_quota`):** `configuration()` принимает только `int` в диапазоне `0 <= rq <= target - core` (по умолчанию `0`).
* **`H8` (Синхронизация контракта и `PASTE/*.txt`):** Синхронизированы `DATA_CONTRACT.md`, `SCORING.md`, `TAXONOMY.md`, `SYSTEM.md`, `PROMPTS/*`, шаблоны, `PASTE/*.txt` и `input_hashes` в `starter_tasks/CAL-SEARCH-01..04.json`.
