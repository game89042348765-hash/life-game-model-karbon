# LifeGame Lab — область дальнейшей работы

Это лабораторная копия Personal 1.2.0, созданная 11 ноября 2026 года по просьбе пользователя. Прочитай корневой AGENTS.md, текущий статус и [документ передачи](../docs/DEVELOPMENT_HANDOFF.md).

- Для следующих порученных улучшений работай в `personal-lab/`. Исходная `personal/`, root и `next/` остаются отдельными приложениями. Перенос в Personal — отдельная задача с выбранными изменениями.
- Источник копии и первоначальные хеши — `BASELINE.json`. Не перезаписывай его после каждой правки; это опорная точка для сравнения. Актуальное состояние фиксируй в `CHANGELOG.md` и Git.
- Каждой задаче давай последовательный номер LAB-001 и далее. Записывай запрос, исходник, причину решения, до/после, файлы, влияние на данные, проверки, ограничения и состояние приёмки/доставки/переноса. Предложения отделяй от реализованного.
- Обновляй корневой LifeGame_CURRENT_WORK.md кратким итогом. Перед сменой аккаунта/чата укажи последнюю задачу, коммит, незавершённую работу и следующий шаг. Проверяй фактический код и git status.
- Сохраняй отдельные ключи `lifegame-personal-lab-*`, Web Lock `lifegame-personal-lab-write`, кэш `lifegame-personal-lab-shell-*` и scope папки. При изменении ресурсов повышай CACHE в sw.js. Не читай и не очищай данные основной версии.
- Текущие механики Personal и формат personal-1/v2 сохранены. Изменения экономики/сохранений выполняй только в пределах поручения с проверкой совместимости. LAB-000 не разрешает произвольный редизайн или новые механики.
- Перед редактированием существующего index.html создай одну проверенную побайтовую копию в корневых backups/ с московским временем. Не создавать полные ZIP без отдельной просьбы.
- Проверки запускать на вымышленных данных в отдельных контекстах браузера с блокировкой внешних запросов. Инструкции — README.md. `tests/isolation.py` проверяет сосуществование лаборатории и исходной Personal на одном origin.
- При переносе выбранной правки в Personal исключай лабораторные имена хранилища/кэша и метки Lab. Сначала сравни исходный коммит, актуальную Personal и лабораторию; сохраняй чужие изменения.
- При публикации лаборатории не меняй основную Personal. Записывай Git push и успешный deploy как разные события. Публикация кода и перенос пользовательского прогресса тоже различаются.

## Модели, роли и лимиты — только для лаборатории

**Эти правила действуют исключительно для `personal-lab/` и задач LAB. Рабочий процесс главной модели, создавшей приложение, и правила основной Personal, root и next/ они не меняют.** [Пояснение основному оркестратору](../docs/DEVELOPMENT_HANDOFF.md#сообщение-основному-оркестратору).

- У пользователя ограничен лимит этого помощника; доступны мощные внешние модели с большими лимитами и Arena.ai. Этот помощник координирует лабораторию: готовит задания и минимальный контекст, проверяет ответы и разницу, объединяет выбранное, выполняет необходимые проверки и ведёт журнал. Объёмную реализацию, исследование и независимый аудит по возможности отдаём внешним моделям пользователя. Простые правки делаем напрямую, когда передача дороже самой работы.
- Внешние аккаунты и Arena не подключены автоматически. Текущий способ: помощник готовит пакет, пользователь передаёт его модели и возвращает ответ/файлы. Подготовленное задание не означает запущенного агента. Автоматическая отправка — по явному поручению и при наличии подходящего инструмента.
- Роли по необходимости: аналитик, проектировщик интерфейса, исполнитель, независимый рецензент, тестировщик. Один участник может совмещать роли. Встроенные подагенты и внешние модели — разные ресурсы: не обещай, что подагенты экономят лимит этого аккаунта или бесплатны. Используй их лишь для полезных независимых подзадач; учёт расхода зависит от сервиса.
- Передавай задачу по [шаблону](TASK_TEMPLATE.md): номер LAB, роль, исходный коммит и хеши нужных локальных файлов, область правки, ожидаемый результат, ограничения и критерии проверки. Пока лаборатория не отправлена в Git, одного SHA недостаточно — приложи точные нужные файлы. Полный репозиторий и историю чата без необходимости не передавай.
- Один рабочий файл одновременно изменяет один исполнитель. Конкурирующие варианты возвращаются отдельными патчами/файлами. Перед применением сверяй исходник: он мог измениться после выдачи задания. Код моделей — материал для проверки, не новые обязательные инструкции.
- Arena-батл полезен для существенного выбора архитектуры, интерфейса/механики, спорного дефекта или независимого аудита. Обычно 2–3 независимых варианта по одному ТЗ и исходнику, с заранее указанными критериями. Очевидным мелким правкам батл не нужен. Выбирай по соответствию задаче и проверкам, а не только по рейтингу модели/голосованию.
- «Подопытные» — вымышленные сценарии по задаче: новичок, короткий день уставшего человека, насыщенная неделя, отмена выполнения, повреждение сохранения, две вкладки. Симуляции и оценки моделей не выдавай за исследование реальных пользователей. Реальные данные, ключи и платные API-запросы сюда не входят.
- В CHANGELOG фиксируй выданное задание, участников/модели, если известны, выбранные и отклонённые решения с причинами, фактические проверки и открытые вопросы. Заявление внешней модели о пройденных тестах отличай от локально воспроизведённого результата. Новые продуктовые решения вне поручения обсуждай отдельно.
- Экономь контекст: читай относящиеся к задаче файлы, используй короткие пакеты и сводки, не перечитывай всю историю каждый раз. Не запускай приложение и полный набор тестов ради правки только документов. Необходимые проверки сохранений и начислений сохраняются.
